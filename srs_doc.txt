I. Overall Requirements

1. Context Diagram

The Context Diagram provides an overview of the NEXLOG system and shows how the system interacts with external actors and services.

The actors are the Manager, Dispatcher, Driver, Administrator and Guest. The external services are Google Maps Platform, Cloudinary, the Vehicle GPS System, the AI service (Google Gemini), the email service and the vendor systems.

Figure 1. Context Diagram of NEXLOG System

2. Main Business Flow

The five flows follow an order from intake to closing, with vendors, incidents and cancellations. Grey boxes are actor steps, yellow italic boxes are system steps, diamonds are decisions, dashed boxes are done outside the system.

2.1 Order Intake (BF-01)

Trigger: A customer fills in the order form on the website.

End condition: The order is Confirmed: the customer documents are verified and the order contract is signed (go to BF-02).

Figure 2. Order Intake (BF-01)

2.2 Trip Planning and Assignment (BF-02) 

Trigger: An order is Confirmed.

End condition: The trip is created and sent to the driver (go to BF-03).

Figure 3. Trip Planning and Assignment (BF-02)

2.3 Trip Execution, Delivery and Closing (BF-03)

Trigger: The driver gets a new trip with its trip documents (end of BF-02).

End condition: Each order is Delivered, or Delivered (Exception) with its cargo stored at an ALS warehouse. The system sets the trip Completed and the truck Available again.

Figure 4. Trip Execution, Delivery and Closing (BF-03)

2.4 Incident and Compensation Handling (BF-04)

Trigger: A driver reports an incident during a trip (BF-03), or a customer sends a claim on the tracking page after delivery.

End condition: The trip goes on with the same truck, or with another truck or driver on the same trip, or the Manager approves or rejects the claim.

Figure 5. Incident and Compensation Handling (BF-04)

2.5 Order Cancellation (BF-05)

Trigger: A customer asks the Dispatcher to cancel an order.

End condition: If the cargo is loaded, the order goes on to delivery (BF-03). Otherwise the order is Cancelled with its fee, and the truck and drivers are released.

Figure 6. Order Cancellation (BF-05)

II. Use Case Specifications

1. Order Management

1.1 Submit Order Form (UC-08)

 |  |  |  | 

Primary Actors |  |  |  | 

Guest |  |  |  | 

Secondary Actors |  |  |  | 

Google Maps Platform

 |  |  |  | 

Description |  |  |  | 

As a customer, I want to send my orders through a link without an account, so that ALS gets the full order data at once.

 |  |  |  | 

Preconditions |  |  |  | 

The Guest has a valid order form link of a Dispatcher (BR-44).

 |  |  |  | 

Normal Flow |  |  |  | 

1. Guest opens the order form link.

2. System shows the empty Order Form.

3. Guest enters the customer details: customer name, phone and email. The tax code and the address are optional; the Dispatcher completes them before confirming.

4. Guest chooses import or export and enters the order: the ALS warehouse, the other address, the receiver, the requested pickup date, the truck type, the loading request, the cargo lines, the customs service and the price.

5. Guest clicks Thêm hàng hóa to add another cargo line, or goes to step 6.

6. Guest clicks Xác nhận tạo đơn.

7. System checks the fields and the weight (BR-38).

8. System matches the customer by tax code, or by email when no tax code is given. Otherwise it creates a customer (BR-44).

9. System finds the map position of each address (API-05) and matches it with the saved Locations.

10. System saves the order as Draft, gives it to the Dispatcher of the link (BR-20) and notifies that Dispatcher.

11. System shows MSG52.

 |  |  |  | 

Alternative Flows |  |  |  | 

Step 7a – Wrong data

System shows MSG02, MSG03 or MSG04 under the field. The form keeps the data.

Step 7b – Cargo too heavy

The weight is over 4,000 kg. System shows MSG81.

Step 7c – Other warehouse without a name

System shows MSG73 (BR-54).

Step 9a – Address not found

The order is still saved. The Dispatcher fixes the Location in UC-40 (MSG54).

Step 10a – Too many sends

System shows MSG37 (BR-44).

 |  |  |  | 

Postconditions |  |  |  | 

• The order is Draft and linked to the customer and the Dispatcher.

• It has no trip and no tracking link yet.

 

1.2 Manage Orders (UC-03)

 |  |  |  | 

Primary Actors |  |  |  | 

Dispatcher |  |  |  | 

Secondary Actors |  |  |  | 

Google Maps Platform

 |  |  |  | 

Description |  |  |  | 

As a Dispatcher, I want to check a draft order, agree the price with the customer, get the customer documents and the signed order contract, and confirm the order, so that the order can be planned.

 |  |  |  | 

Preconditions |  |  |  | 

• Dispatcher has logged in.

• A Draft order exists (sent by the customer on the website, or entered by the Dispatcher).

 |  |  |  | 

Normal Flow |  |  |  | 

1. Dispatcher opens a Draft order from the Order List.

2. System shows Order Details with the order data.

3. Dispatcher checks the data and the Locations, and edits them if needed. If the customer data is wrong, the Dispatcher corrects it after asking the customer.

4. System runs UC-07 Calculate Route Distance & Time and shows the trip time and the suggested number of drivers (BR-04).

5. Dispatcher completes the tax code and the address, checks that the cargo is not dangerous (BR-38) and quotes the price by Zalo or Hotline. The Dispatcher also asks about grouping and the customs service.

6. The customer agrees to the quote, says yes or no to the grouping, and says yes or no to the customs service. The Dispatcher updates Customs service required if needed.

7. Dispatcher checks the agreed price from the form (BR-01) and sets the required customer document types (BR-06). If the customer chose the customs service, the Dispatcher adds its fee as an extra fee (BR-30).

8. Dispatcher clicks Send Tracking Link. System creates the tracking token (BR-21), emails the tracking link and the required document list to the customer and shows MSG08.

9. The customer uploads the customer documents (UC-02). If the customer chose the customs service, the Dispatcher prepares and uploads them. The Dispatcher checks and confirms them in UC-05 Manage Customer Documents.

10. When the documents are Documents Verified, the Dispatcher clicks Create Contract. System makes the order contract from the order data and the agreed price (BR-45). The Dispatcher sends it to the customer, who signs it.

11. Dispatcher uploads the signed contract and clicks Confirm Order. System checks the verified documents, the agreed price and the signed contract (BR-50) and asks to confirm (MSG57).

12. System sets the order to Confirmed and links it to the Active transport contract of the customer (BR-47). The order can now be planned (UC-09).

 |  |  |  | 

Alternative Flows |  |  |  | 

Step 1a – Order by phone

Dispatcher clicks New Order on the Order List, fills the Order Form for the customer and continues at step 2.

Step 4a – Distance service not available

System shows MSG34. The order stays Draft. The Dispatcher tries again later.

Step 6a – The customer does not agree

Dispatcher clicks Cancel Draft. The order becomes Cancelled with no fee (BR-18).

Step 7a – Documents not known (extension point)

UC-39 Ask Document Assistant. The Dispatcher adds the chosen documents to the list.

Step 7b – No document needed

The Dispatcher ticks No document needed. At step 8 the tracking link is sent without a document list, and the Dispatcher goes to step 10.

Step 8a – Price or document list missing

System shows MSG02 or MSG43.

Step 8b – Email not sent

The order is still saved. System shows MSG32 with the tracking link. The Dispatcher sends it by Zalo.

Step 11a – Signed contract missing

System shows MSG67.

 |  |  |  | 

Postconditions |  |  |  | 

• The order is Confirmed, with its verified documents, price, signed contract, linked transport contract and tracking link.

 

1.3 Manage Customer Documents (UC-05)

 |  |  |  | 

Primary Actors |  |  |  | 

Dispatcher |  |  |  | 

Secondary Actors |  |  |  | 

Cloudinary

 |  |  |  | 

Description |  |  |  | 

As a Dispatcher, I want to check and verify the customer documents, so that the order contract can be made.

 |  |  |  | 

Preconditions |  |  |  | 

• Dispatcher has logged in.

• The order is Draft and its tracking link and document list were sent (UC-03).

 |  |  |  |

11. Background Job Inventory

11.1 Purge Expired Files and Data (JOB-01)

Trigger: Scheduled — every day at 2:00 AM

Purpose: Deletes files and GPS tracks when the retention period of their type is over.

Processing steps:

1. Read the retention period of each data type (BR-22 lists the types).

2. For each type, find the records that are past their period. For the files of an order, the period starts when the order is Delivered or Cancelled.

3. Skip orders that have a Pending compensation claim.

4. Delete each file in Cloudinary (API-03). Mark the file record as Purged. For POD and seal & plate photos, also delete the receiver name and the saved position. Keep the order data.

5. Delete the old GPS track points, except the tracks of trips with a Pending claim.

6. Log how many orders, files and rows were purged.

Failure behavior:

 |  |  |  | 

Scenario |  |  |  | 

System behavior

 |  |  |  | 

Cloudinary is not available or returns an error |  |  |  | 

The file record does not change. The job tries again in the next run and logs a warning.

 |  |  |  | 

The retention period of a type is not set |  |  |  | 

The job deletes nothing of that type and logs a critical error.

 |  |  |  | 

No old records |  |  |  | 

The job ends. This is normal.

11.2 Pull Truck Locations from GPS (JOB-02)

Trigger: Scheduled — every 1 minute

Purpose: Gets the location of trucks on active trips from the Vehicle GPS System. It is used for Trip Monitoring, the position check (BR-36), Replay Trip and the driving time (BR-34).

Processing steps:

1. Find trucks with an Accepted or In Progress trip.

2. Call the Vehicle GPS Location API (API-04) with their truck IDs.

3. Save the latest position, speed and time for each truck. Add the point to the track of its trip.

4. Count the continuous driving time of the drivers of each trip from the speed (BR-34). A gap in the GPS data between Left and Arrived counts as driving. Alert the Dispatcher when a driver is close to 4 hours (MSG65).

5. Find trips that are not done when the shift of a driver ends, and alert the Dispatcher (MSG83).

Failure behavior:

 |  |  |  | 

Scenario |  |  |  | 

System behavior

 |  |  |  | 

The GPS API cannot be reached |  |  |  | 

The last known position and its time are kept. Trip Monitoring shows "last updated". The job tries again in the next run. The track has a gap for that time. A gap between Left and Arrived counts as driving (BR-34).

 |  |  |  | 

The provider does not know the truck |  |  |  | 

The job skips the truck and logs a warning.

11.3 Flag Orders Waiting Too Long (JOB-03)

Trigger: Scheduled — every 15 minutes

Purpose: Flags orders that stay Draft, or Confirmed without a trip, longer than the set limit, and orders past the document deadline (BR-25), for the Manager’s Order Workload.

Processing steps:

1. Read the limits (values set by ALS).

2. Find Draft orders, and Confirmed orders without a trip, that stay in that state longer than the limit and flag them.

3. Find orders whose customer documents are not Documents Verified by the document deadline, flag them and alert the Dispatcher (MSG41).

4. Remove the flags that no longer apply.

Failure behavior:

 |  |  |  | 

Scenario |  |  |  | 

System behavior

 |  |  |  | 

The database cannot be reached |  |  |  | 

The job tries 3 times, 30 seconds apart, then logs a critical error. Flags are updated in the next good run.

11.4 Clean Up Sessions and Notifications (JOB-04)

Trigger: Scheduled — every day at 3:00 AM.

Purpose: Deletes old sign-in sessions and old notifications, so the tables stay small.

Processing steps:

1. Delete sessions that expired or were signed out more than 7 days ago.

2. Delete notifications older than 90 days.

3. Log how many rows were deleted.

Failure behavior:

 |  |  |  | 

Scenario |  |  |  | 

System behavior

 |  |  |  | 

The database cannot be reached |  |  |  | 

Nothing is deleted. The job runs again the next day.

 

11.5 Remind Expiry Dates (JOB-05)

Trigger: Scheduled — every day at 6:00 AM.

Purpose: Warns the Manager before a truck inspection, a truck insurance or a driver licence expires. It also stops the use of a truck whose inspection has expired.

Processing steps:

1. Read the warning period (a setting).

2. Find trucks whose inspection or insurance, and drivers whose licence expires within the warning period.

3. Send one alert to the Manager for each item. Do not repeat the same alert on the same day.

4. Set a truck whose inspection has expired to Inactive.

5. Log how many alerts were sent.

Failure behavior:

 |  |  |  | 

Scenario |  |  |  | 

System behavior

 |  |  |  | 

The database cannot be reached |  |  |  | 

Nothing changes. The job runs again the next day.

 |  |  |  |

Description

 |  |  |  | 

Formats |  |  |  | 

Dates are dd/MM/yyyy and times are HH:mm, Vietnam time (UTC+7). Money is in VND with thousand separators. Weight is in kg and sizes are in cm.

 |  |  |  | 

Settings |  |  |  | 

The Administrator can change the settings listed on the System Settings screen (III, 10. System Administration). The legal limits of BR-34 are shown but cannot be changed.
