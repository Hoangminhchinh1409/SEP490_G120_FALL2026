I. High Level Design

1. Software Architecture

NEXLOG uses a three-tier architecture. One Next.js web app serves the public website and the staff portals, and also the Driver PWA. It calls one Express REST API. The API stores data in PostgreSQL, hosted on Supabase, and calls external systems through adapters. A separate worker process runs the five scheduled jobs (JOB-01 to JOB-05).

Why this style. The system is for one company, so one deployable API (a modular monolith) is easier to build, test and run than many services. The worker is a separate process, so a slow job never blocks a user request. The Driver PWA keeps its own queue on the phone, because trucks lose the signal (BR-27).

Technology. Node.js and Express 5 in JavaScript, PostgreSQL 16, Prisma as the data access layer, Next.js for the web app, Cloudinary for files, JWT for sign-in. Supabase is only the PostgreSQL host. Auth and storage of Supabase are not used.

Main design decisions

·      One origin for the browser. The web app calls the API with cookies (JWT in an httpOnly cookie). CORS allows only the web origin and credentials.

·      Prisma for data access. One schema file describes the 36 tables. Migrations keep every developer on the same schema. A few rules that need SQL (no overlapping shifts, one open trip for each truck) are written in the migration files.

·      Business rules live in services. A controller only reads the request and sends the answer. A service holds the rules (BR-xx) and the transaction. A repository holds the Prisma calls.

·      ETA is our own code. Google gives driving time. The ETA of each stop is calculated in the trips module (BR-04), at planning and again from JOB-02.

·      The tracking page is public but narrow. It uses a random token, shows milestones only, and never shows the seal & plate photo or the POD (BR-13, BR-21).

Table 2. Package descriptions

Naming conventions.

·      API module folder: lowercase plural noun (orders, trips).

·      Files by layer: orders.routes.js, orders.controller.js, orders.service.js, orders.repository.js, orders.schema.js.

·      Classes: PascalCase with the layer name (OrderService, TripController, RoutesAdapter).

·      Web: page folders lowercase, component files PascalCase, hooks start with use.

Dependency rule. Calls go one way only:

·      driver → trips, orders, documents, incidents

·      trips → orders, fleet, locations, vendors

·      incidents → trips, orders, claims

·      tracking → orders, documents, claims

·      dashboard, monitoring → read from all

Nothing calls driver or tracking. A two-way flow goes to workflows. A controller never writes SQL. A module reads another module’s data only through its service.

Other conventions. Tables and columns are snake_case. Prisma models are PascalCase and map to the table names with @@map. Errors use one JSON shape: code, message (an MSG number) and fields. Every write that changes an order or a trip status also writes the status history table and the activity log in the same transaction.

3. Database Design

Each entity of the Report 3 ERD becomes a table. Parts that Report 3 keeps inside an entity (cargo lines, notes, stops, events, evidence, GPS track, shifts) get their own table. Two technical tables are added: sessions and code_counters. Total: 36 tables.

·      Primary keys are BIGSERIAL (SERIAL for small reference tables). Business codes (order_code, trip_code, waybill_number) are unique text columns.

·      Money is BIGINT in VND. Weight is NUMERIC in kg, sizes are in cm, coordinates are NUMERIC(9,6). Times are TIMESTAMPTZ in UTC; the screens show Vietnam time.

·      Order and Trip are many-to-many through trip_stop_orders. One pickup stop can serve several orders of the same customer (BR-05): the driver records the stop events once, but each order keeps its own weight, seal and POD (BR-29). A drop-off stop serves one order.

·      Status values are PostgreSQL enums. Every status change of an order or a trip is also a row of order_status_history or trip_status_history (BR-51).

·      The price is the agreed price on the order (BR-01). There is no rate card and no trip price. The route reference price is calculated when needed and is not stored.

·      A waybill is its own table, because it has its own status (Valid or Replaced) and its own file. A trip has one Valid waybill at a time; a truck or driver change makes a new one (BR-35).

·      Truck and driver changes on a trip are rows of trip_trucks and trip_drivers with a replacement reason and release time. The trip itself stays the same (BR-10, UC-15).

·      Every foreign key has an index. Files are stored as Cloudinary public IDs or links, never as blobs. Only trucks are soft-deleted (deleted_at); other records are kept or purged by JOB-01 (BR-22).

Rules written in SQL migrations

Prisma cannot describe the rules below. They are created in the migration files with raw SQL (the btree_gist extension is needed for the exclusion rules). A test in the first sprint checks that prisma migrate shows no false drift.

-- no overlapping Requested/Approved shifts of one driver (BR-60)

ALTER TABLE driver_shifts ADD CONSTRAINT driver_shifts_no_overlap

  EXCLUDE USING gist (driver_id WITH =, tstzrange(start_time, end_time) WITH &&)

  WHERE (status IN ('REQUESTED','APPROVED'));

-- one unfinished trip for each truck and driver (BR-08, data rule)

CREATE UNIQUE INDEX trip_trucks_one_open ON trip_trucks (truck_id) WHERE released_at IS NULL;

CREATE UNIQUE INDEX trip_drivers_one_open ON trip_drivers (driver_id) WHERE released_at IS NULL;

-- one Valid waybill for each trip (BR-35)

CREATE UNIQUE INDEX waybills_one_valid ON waybills (trip_id) WHERE status = 'VALID';

-- one POD for each order

CREATE UNIQUE INDEX evidences_one_pod ON delivery_evidences (order_id) WHERE type = 'POD' AND purged = false;

-- one Active contract for each customer; a contract belongs to one party

CREATE UNIQUE INDEX contracts_one_active ON transport_contracts (customer_id) WHERE status = 'ACTIVE' AND customer_id IS NOT NULL;

ALTER TABLE transport_contracts ADD CONSTRAINT contract_one_party CHECK ((customer_id IS NULL) <> (vendor_id IS NULL));

-- a customer site has a customer

ALTER TABLE locations ADD CONSTRAINT site_has_customer CHECK (type <> 'CUSTOMER_SITE' OR customer_id IS NOT NULL);

-- cancellation tiers of one contract do not overlap

ALTER TABLE contract_cancellation_tiers ADD CONSTRAINT tiers_no_overlap

  EXCLUDE USING gist (contract_id WITH =, int4range(hours_from, COALESCE(hours_to, 100000)) WITH &&);

II. Detailed Code Design

The three features with the most integrations are designed in detail: order intake, trip planning with ETA, and GPS with driving hours. Each has a class diagram, sequence diagrams and the rules of each step. External systems are called through adapters.

The Guest or the Dispatcher fills in the Order Form. The order is saved as Draft. The Dispatcher then sets the price and the required documents, sends the tracking link, verifies the customer documents, makes and uploads the signed order contract, and confirms the order (BR-44, BR-45, BR-50).

Main flow

·      1. The Guest opens the order form link of a Dispatcher. The API finds the Dispatcher by the order form token (BR-44).

·      2. The form is sent. OrderService validates it, finds or creates the customer, resolves the two Locations (saved ones, or new ones geocoded), calculates the chargeable weight of each cargo line.

·      3. In one transaction: insert the order with status DRAFT, its cargo lines, the first order_status_history row. The OrderID comes from code_counters (prefix + yyMMdd + number).

·      4. NotificationService alerts the responsible Dispatcher (MSG52). The order has no trip and no tracking link yet.

·      5. The Dispatcher opens Order Details. The API calls Calculate Route Distance & Time (see Trip Planning) and returns distance, trip time and the suggested number of drivers. A Draft only gets these numbers (BR-46).

·      6. The Dispatcher enters the agreed price and the required document types (or ticks “no documents”). Send Tracking Link creates the tracking token and emails the link and the list (BR-21).

·      7. The customer uploads files (Guest, by token) or the Dispatcher uploads on behalf. Each file goes straight to Cloudinary with a signature from the API; the API saves the link.

·      8. The Dispatcher confirms or rejects each file, then Confirm Documents. Every required type needs a file. The order becomes Documents Verified; documents can no longer be deleted.

·      9. Create Contract makes the order contract file. The Dispatcher uploads the signed contract.

·      10. Confirm Order checks BR-50 in a transaction: documents verified (or none needed), agreed price set, signed contract present. It links the Active transport contract of the customer, sets CONFIRMED and writes the history row. If a check fails the API returns MSG02 (no price), MSG11 (a document type has no file) or MSG67 (no signed contract). MSG57 asks the Dispatcher to confirm.

·      Concurrency. orders.version is checked on every update. A second user who saves an old version gets a conflict error and reloads the order.

·      After pickup cargo, price and Locations cannot change (BR-32, MSG33). A change before pickup that affects a trip recalculates the route.

2. Trip Planning, ETA and Assignment

A Confirmed order is planned into a trip. The system calculates the route distance, the trip time and the ETA of each stop (BR-04). The Dispatcher chooses the truck, one or two drivers, the stop order and the planned start, then assigns. The system makes the waybill and sends the trip to the driver (BR-35, BR-23).

·      4. The Dispatcher picks the truck, the number of drivers, the drivers, the planned start and the stop order. The screen shows the ETA of each stop and warns when an ETA is outside the receiving hours of the Location (MSG84).

·      5. Assign: TripService locks the rows, checks payload, shifts and open trips again, creates the trip (DISPATCHED), the stops, the truck and driver rows; sets the orders ASSIGNED; reserves the truck (BR-24).

·      6. WaybillService stores the waybill row (VALID) with the trip snapshot. The trip documents become available to the Dispatcher and the driver.

·      7. The driver gets the trip in My Trips and an alert. The tracking page now shows Truck assigned (BR-14).

·      8. If no fleet truck is free, the Dispatcher uses Hand Over to Vendor instead (UC-10, see IV.3.3).

·      Only the planned ETA is saved (trip_stops.planned_arrival). The latest ETA is saved in latest_eta and is for staff only; it is not shown on the tracking page and there is no late flag (BR-04).

·      Driver rest breaks are not planned in the trip time (BR-04).

A3 and A4. Trip time and ETA (BR-04)

Input: the stops in order (Location, stop type, weight loaded or unloaded at the stop), the planned start T0, the truck, and the settings.

t = T0

for each stop k (k = 1..n):

    leg = Routes.computeRoutes(stop k-1 -> stop k, departure = t, traffic = TRAFFIC_AWARE)

    drive_k   = leg.duration x truck_time_factor          # 1.2 for trucks

    arrive_k  = t + drive_k

    if arrive_k outside receiving hours of the Location: warn MSG84 (no waiting is added)

    stop_k    = base_stop_time(stop k) + minutes_per_tonne x weight_k

                # base: 60 min at an ALS import warehouse, 15 min elsewhere

                # the Dispatcher may type another stop time

    t = arrive_k + stop_k

trip_time = t - T0

if trip_time > 8 h: suggest 2 drivers

Recalculation (A4). It runs after a stop event, after a truck change, and every 5 minutes for trips In Progress (JOB-02).

origin = last truck GPS point if it is less than 5 min old

         else the Location and Left time of the last finished stop

skip if no new event AND the truck moved less than 500 m since the last run

legs = one Routes call: origin -> remaining stops (as intermediates), departure = now

rest_here = max(0, planned stop time - (now - Arrived))   # only if the truck is at a stop

ETA of each remaining stop = now + rest_here + legs and stop times before it

save latest_eta on each remaining stop; the planned ETA is never changed

Output: planned ETA per stop (saved at assignment) and latest ETA (saved at each run). Settings: truck time factor, stop times, minutes per tonne, two-driver limit, recalculation interval, skip distance.

Why:

·      Delivery platforms (Onfleet) build the ETA from a routing service plus a service time per stop.

·      Routes gives car times; the truck factor covers the slower truck.

·      One Routes call per trip and the 500 m skip rule keep the API cost low.

A6. Driving time from the GPS track (BR-34)

Input: GPS points of the truck (time, position, speed) sorted by time, the trip events, and the drivers of the trip.

for each pair of points (p_i, p_i+1):

    dt = time difference

    v  = speed of p_i, or distance(p_i, p_i+1) / dt if the speed is empty

    if dt <= 5 min:

        if v > 3 km/h: add dt to driving, add dt to continuous

        else:          add dt to standing

    else (GPS gap):

        if the gap is between a Left event and the next Arrived event: count dt as driving

        else: do not count it

    if standing time without a break >= 15 min: it is a break, continuous = 0

    if continuous >= 4 h and no alert since the last break: alert MSG65

on a 2-driver trip the driving time counts for both drivers

Output: driving time per driver per day, continuous driving time, alerts. The 10-hour day and 48-hour week limits are checked against the approved shifts when a driver is assigned (A5). Settings: speed threshold 3 km/h, break 15 minutes, gap 5 minutes; the 4 h, 10 h and 48 h limits are law and are locked.

Why:

·      The limits are law: Law 36/2024/QH15 Art. 64 and Circular 05/2024/TT-BGTVT.

·      A tachograph reads the wheel; NEXLOG only has GPS points, so it uses a speed threshold and a minimum stop length.

·      A gap on the road counts as driving, so a lost signal never hides driving time.

A9. 3D load plan (BR-43, BR-56)

Input: the truck box (length L, width W, height H in cm, payload in kg), the stops in order, and the cargo lines of the trip (quantity, length, width, height, weight, stackable, drop-off stop number). Axes: x goes from the front wall (x = 0, next to the cab) to the door (x = L), y across the box, z up.

1. blocks = each package of each cargo line with a size (quantity 3 -> 3 blocks)

   lines without a size are listed and only their weight is counted

   more than 500 blocks: draw the first 500, list the rest

2. sort blocks by:

   drop-off stop number, last stop first      # last drop-off goes deepest

   then not stackable first, then bigger base area, then heavier

3. extreme points EP = {(0,0,0)}

4. for each block b:

     best = none

     for each EP p and each turn of b (L x W or W x L; height never turns):

        put the corner of b at p and keep the position if:

          a. b is inside the box

          b. b does not overlap any placed block

          c. support: if z > 0, at least 75% of the base of b lies on tops of

             placed blocks at height z, and every block under b is stackable

             and is delivered at the same stop as b or later

          d. reach: no placed block that is delivered after b lies between b

             and the door with an overlap in y and z (b can be unloaded first)

        score = (x + length of b, z, y)          # deepest, then lowest, then left

        keep the position with the smallest score

     if best = none: mark b as not fitting (red, MSG66)

     else: place b, add the three projected points of its corners to EP,

           remove points that are now inside a block

5. result: position and turn of each block, blocks that do not fit,

   used volume % = placed volume / box volume, total weight / payload

Output: a JSON list of blocks (order, stop, x, y, z, length, width, height, colour by stop) that the web draws with Three.js. Nothing is saved. The plan never blocks the assignment. Settings: support share 75%, block limit 500. Cost: about n² × points; 500 blocks take well under one second.

Why:

·      The three rules (last in first out, nothing on non-stackable cargo, minimum supported base) are the standard rules of loading research (3L-CVRP, Gendreau et al. 2006).

·      Extreme points (Crainic, Perboli and Tadei 2008) find the free corners fast.

·      Load planners such as xflp add a search step and axle checks. NEXLOG keeps only the greedy step: the plan is a guide and the loader decides.

A10. Position check at a stop (geofence, BR-36)

Input: the driver event (type, phone time, phone latitude and longitude, accuracy in metres from the browser), the Location of the stop (latitude, longitude, radius or empty), and the truck GPS points.

r = radius of the Location, or the default radius (setting, 150 m)

if the phone gives no position (no permission, or no fix within 10 s):

    save the event, distance = empty, outside_radius_flag = true, alert MSG50

else:

    d = haversine(phone position, Location)

        # d = 2R asin( sqrt( sin²(dφ/2) + cos φ1 cos φ2 sin²(dλ/2) ) ), R = 6 371 000 m

    margin = min(accuracy, 50 m)            # allow for phone GPS error

    outside = d > r + margin

    truck_point = truck GPS point closest to the phone time, within 2 min

    truck_inside = truck_point exists and haversine(truck_point, Location) <= r

    save the event with distance_m = d, outside_radius_flag = outside

    if outside: alert MSG50 with d and r, and add "truck GPS inside the radius"

                when truck_inside is true

never refuse the event

Output: the flag and the distance on the trip event, the alert, and the red marker on Trip Monitoring and Replay Trip. Dwell time for Driver Performance (UC-43) = Left − Arrived of the same stop. Settings: default radius, accuracy margin, phone fix timeout.

Why:

·      TMS products (Qargo, Yojee) use one default radius with a radius per location, and compare the geofence time with the time the driver tapped.

·      Android advises a radius of at least 100–150 m because phone positions are often 20–50 m off. Hence the 150 m default and the accuracy margin.

·      The truck GPS is a second witness: it tells a phone error from a false record.

4. Offline Sync (Driver PWA)

·      Queue. Every driver action is saved in IndexedDB with a client action ID, the phone time and the position, then shown on screen at once. At most 50 actions can wait (MSG39).

·      Send. When the browser is online, or when the driver taps Sync Now (iPhone), the queue is sent in order. The server saves each action in a transaction. A repeated client action ID returns the first result.

·      Clock. A phone time in the future, or off by more than the phone clock limit, is replaced by the server time and flagged (BR-27).

·      Photos. A photo is uploaded to Cloudinary with its client action ID as the public ID. Then the action that refers to it is sent.

·      Conflict. If the trip changed while the phone was offline (truck or driver changed, trip cancelled), the server saves the action, marks it and alerts the Dispatcher (MSG38).

·      Documents offline. After the driver opens the waybill and the customer documents once, they are kept in the cache; they are removed when the trip is Completed or the waybill is Replaced.
